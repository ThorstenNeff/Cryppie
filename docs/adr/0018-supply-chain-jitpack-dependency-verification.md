# ADR-0018 — Supply-Chain-Policy: JitPack für WC-Android + Dependency-Verification

- **Status:** **Accepted** (2026-06-19) — WalletConnect-Android (L4 Chunk 3, KAN-62); Supply-Chain-Posture vom User ratifiziert (WC im Erst-Release).
- **Kontext:** Die WalletConnect-Android-Integration ([[0015]]) nutzt das offizielle **Reown WalletKit**. Dessen Artefakte (`com.reown:*`) liegen auf **Maven Central**, aber ein Teil der **Transitiven** — `com.walletconnect.Scarlet`, `com.github.multiformats:java-multibase`, `com.github.komputing.kethereum` — ist **upstream nur über JitPack** verfügbar, **nicht** auf Central. JitPack baut Artefakte **on-demand aus Source**: Git-**Tags sind mutierbar** (kein immutabler Artefakt-Vertrag), Artefakte sind i. d. R. **nicht vom Upstream PGP-signiert**, und es besteht ein **Verfügbarkeits-Risiko** (Ausfall ⇒ Build kaputt). Für eine **non-custodial Wallet** ([[0005]]) ist die Lieferketten-Integrität sicherheitskritisch; zwei der Deps (`kethereum`, `multibase`) sind **krypto-nah**.
- **Entscheidung:** Scoped JitPack ist **zulässig — ausschließlich unter folgenden Bedingungen** (alle verpflichtend; ohne (A) **keine Freigabe**):
  - **(A) Gradle Dependency-Verification = harter Gate.** Committetes `verification-metadata.xml` (strict), erzeugt via `./gradlew --write-verification-metadata sha256`. JitPack-Artefakte werden **sha256-gepinnt** (checksum-only, `reason="not signed"`); jede Artefakt-Änderung **bricht den Build** → neutralisiert JitPacks Mutabilität zur Build-Zeit. **Dies ist der eigentliche Kontroll-Hebel.**
  - **(B) Exakte Pins; Commit-Hash-Koordinaten** für die `com.github.*`-Deps statt beweglicher Tags (JitPack baut aus immutablem Commit) → Source-Immutabilität.
  - **(C) Content-gefilterter Repo-Scope** (`includeGroupByRegex` auf `com.github.*` + `com.walletconnect`) → verhindert, dass JitPack Central-Artefakte **shadowt** (Dependency-Confusion-Guard).
  - **(D) PGP wo vorhanden:** `com.reown:*` (Central, signiert) per `<pgp>` verifizieren; JitPack-Transitive checksum-only.
  - **(E) CI fail-closed** mit aktivierter Verification.
  - **Key-Pfad-Invariante (explizit):** Alle Key-/Seed-/Signatur-Ops bleiben in **`:wallet`** (secp256k1, on-device, Keystore, [[0005]]/[[0009]]); **`:walletconnect` erhält nie Seed/Private-Key**, nur Transport/Session + das **Ergebnis** der in `:wallet` erfolgten Signatur. ⇒ Selbst eine kompromittierte krypto-nahe Transitive ist **nicht auf dem Key-Pfad** → Blast-Radius = Transport-/Session-Manipulation, **nicht** Key-Exfiltration. Sicherstellen, dass **kein** Typ aus dem WC-Baum (`kethereum` etc.) auf den Signing-Pfad leakt.
- **Konsequenzen:** Risiko mit (A)–(E) + Invariante = **Medium, vertretbar**; ohne Verification = **High → nicht freigeben**. Build-Zeit-Tamper ist detektierbar; JitPack-Mutabilität entschärft. Verbleibend: Verfügbarkeits-/Wartungslast (neue Pins ⇒ Metadata-Update). **Mittelfristige Härtung:** **Vendored Mirror** — die JitPack-Deps einmalig aus gepinnten Commits bauen, verifizieren und in einen internen **Nexus/Artifactory** (oder committete, verifizierte AARs/local-repo) legen → entfernt die Live-JitPack-Abhängigkeit + löst das Verfügbarkeits-Risiko.
- **Alternativen (verworfen / aufgeschoben):** **JitPack ohne Verification** (verworfen — mutierbare, unsignierte Artefakte auf einer Wallet-Lieferkette); **WC-Android streichen** (verworfen — Kern-Feature, [[0015]]); **sofortiger Vendored-Mirror** (aufgeschoben — Aufwand; interim decken (A)–(E) das Risiko, Mirror als Folgeschritt).
