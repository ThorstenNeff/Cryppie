# ADR-0021 — Server-seitiger API-Key-Proxy (`:server`) für Alchemy/RPC

- **Status:** **Accepted** (2026-06-19, KAN-112) — Key-Proxy im Modul `:server`, lokal (User-Entscheid); Assistent-security-reviewt. *(Hinweis: **0020** ist für die noch offene Charting-Lib-ADR (PRD-04) reserviert — daher die Nummern-Lücke.)*
- **Kontext:** Die gesamte Daten-Schicht (Balances/Prices/Token/NFT/Transfers) holt PRD-03/04 über **Alchemy** + RPC ([[0017]], [[0010]]). Diese Endpunkte brauchen einen **API-Key**. Ein im **Client-Binary** eingebetteter Key (App/Web) ist **extrahierbar** (Decompile/Netzwerk-Mitschnitt/Web-DevTools) → Abuse auf Rechnung des Projekts, Rate-Limit-Exhaustion, im schlimmsten Fall Kosten-/Quota-Schaden. Die Release-Readiness-Analyse (PRD-01/02) hat genau das als **R2 (Alchemy-Key-Dependency)** + Gate **KAN-104** markiert. Gleichzeitig ist Cyppie **non-custodial** ([[0005]]) — der Key-Pfad (Seed/Signatur) ist davon **unberührt**: der Proxy sieht **nie** Seed/Private-Key, nur öffentliche Lese-/Broadcast-Requests.
- **Entscheidung:** Ein **schlanker Forward-Proxy im bestehenden `:server`-Modul** (Ktor) frontet Alchemy/RPC. Der Client spricht **ausschließlich** `/alchemy/...` auf dem Proxy; der Proxy **injiziert den Key server-seitig** in die Upstream-URL und relayt verbatim. Verbindlicher Sicherheits-Vertrag:
  - **(A) Kein Key im Client / kein Key-Echo.** Key lebt nur server-seitig; Client-URLs sind key-frei (`AlchemyProxyConfig`, getestet). `/healthz` meldet nur `keyConfigured: Boolean`, **nie** den Key.
  - **(B) Key-Quelle = JVM-System-Property `alchemyApiKey` (build-gebrückt aus `~/.gradle/gradle.properties`, **nie committet**) bzw. Env `ALCHEMY_API_KEY`** (Deploy). Kein Key im Repo, kein Key im Client-Bundle (verknüpft mit `.gitignore`-Audit **KAN-97**).
  - **(C) Kein Open-Relay.** Path-gescopte Produkte (NFT/JSON-RPC) validieren das `{network}`-Segment gegen eine **Allow-List** (`eth-mainnet`/`base-mainnet`) → fremdes Netz = `404`. Scheme+Host der Upstreams sind **hartkodiert** (`*.g.alchemy.com`) — keine Weiterleitung an beliebige Hosts.
  - **(D) Per-Client-Rate-Limit** (Fixed-Window, in-memory) — ein Aufrufer kann den Upstream-Key nicht erschöpfen.
  - **(E) Fail-soft / FR-4:** ohne konfigurierten Key bootet der Server, aber Proxy-Calls antworten **`503`** → der Client mappt das auf `AllProvidersFailed` und **degradiert sauber** (keine Werte statt Crash; kein Leak einer Fehlkonfiguration).
  - **(F) Pass-through verbatim:** Methode, Query, Body und **Upstream-Status+Body** werden originalgetreu durchgereicht (`expectSuccess=false`), damit die bestehenden Alchemy-Clients unverändert dahinter funktionieren.
  - **Key-Pfad-Invariante ([[0005]]):** der Proxy ist **read/broadcast-only** Transport; **kein** Seed/Private-Key passiert ihn. Signaturen bleiben on-device in `:wallet`.
- **Konsequenzen:** Der Key ist aus dem Client-Binary **eliminiert** (R2/KAN-104 adressiert); Abuse ist auf Allow-List-Netze + Rate-Limit begrenzt. **Lokal-zuerst** (dev: `http://localhost:8080`, ADR-konform); der Proxy ist die natürliche Naht für ein späteres gehostetes Deployment. **Vor Exposition zu härten** (Deploy-Follow-ups, nicht Erst-Release-blockierend): (1) Rate-Limit auf `X-Forwarded-For` statt Socket-`remoteHost` umstellen + Window-Map-Eviction (sonst global/unbounded hinter LB); (2) `{tail...}` der Data/Prices-Routen gegen erwartete Sub-Pfade allow-listen (Least-Privilege — heute Host-fix, aber Pfad unvalidiert); (3) Max-Request-Body-Cap; (4) **TLS** vor dem Proxy; (5) niemals die Upstream-URL loggen (**enthält den Key**). **Single-Vendor-Restrisiko** (Alchemy-Ausfall) bleibt — durch (E) wenigstens als sauberer Degrade sichtbar.
- **Alternativen (verworfen / aufgeschoben):** **Key im Client** (verworfen — extrahierbar, der eigentliche Auslöser); **restriktiv gescopte Client-Keys + Monitoring statt Proxy** (verworfen für Web/öffentliche Clients — ein exfiltrierter Key bleibt missbrauchbar bis zur Rotation; für native evtl. interim denkbar); **vollwertiges Backend mit Auth/Account** (aufgeschoben — PRD-08; der Proxy ist die minimale Vorstufe, die R2/KAN-104 jetzt löst); **gehosteter Proxy sofort** (aufgeschoben — lokal deckt MVP/dev; Deploy-Härtung (1)-(5) als Folgeschritt).
