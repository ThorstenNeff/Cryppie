# ADR-0023 — Minimal-Backend (PRD-08) v1: API-Gateway + Keycloak + User-Service + Postgres auf dem Mac Mini

- **Status:** **Accepted** (2026-06-19, PRD-08, ratifiziert; Laufzeit-Amend launchd→Compose + F1–F6 entschieden — s. Update unten) — dieser ADR ist der **implementierungsreife Blueprint, den der Backend-Agent als Start bekommt**. Ergänzt [[0022]] (gleicher Host/Caddy) und [[0005]] (Non-custodial).
- **Kontext:** Die Wallet-/Read-Schicht (PRD-00–03) läuft on-device + über den Key-Proxy ([[0021]]/[[0022]]). Die **Social/Platform-Features (PRD-04–07: Market-Data, DCA-Bot, Copy-Trading, Vaults)** brauchen ein **Backend mit Identität** (wer ist der Nutzer, wem folgt er, welche Strategie läuft). PRD-08 (Backend-Auth) war zurückgestellt; mit „Erst-GA = volle Super-App" wird ein **minimales Backend** GA-relevant. Es muss **klein anfangen** (ein Host, kein Ops-Overbau) und die **Non-custodial-Invariante** ([[0005]]) **unangetastet** lassen.
- **Entscheidung:** Ein **schlankes Plattform-Backend v1**, initial auf **diesem Mac Mini** (internet-erreichbar, **hinter demselben Caddy** wie der Key-Proxy, [[0022]] A/B/D — TLS/XFF/127.0.0.1-Bind, neue Upstream-Routes). **Scope v1 (genau vier Bausteine):**
  - **(A) API-Gateway** — ein Eintrittspunkt für die Plattform-APIs (Routing, AuthN-Durchsetzung via Keycloak-JWT-Validierung, Rate-Limit/CORS). Frontet die Feature-Services; der **Key-Proxy ([[0021]]) bleibt seine eigene Route** (read/broadcast-only, kein Auth nötig) — Gateway und Key-Proxy koexistieren hinter Caddy, werden **nicht** vermengt.
  - **(B) Keycloak (Auth)** — OIDC/OAuth2-Identity-Provider für die **Platform-Identität** (Login, Token-Ausgabe, Realm/Clients). Ausschließlich für die **Social/Platform-Features (04–07)**.
  - **(C) User-Service** — Profil/Settings/Social-Graph (das, was 04–07 an Plattform-Nutzerdaten brauchen), hinter dem Gateway, Token-geschützt.
  - **(D) Postgres** — die eine relationale Quelle für (C); Schema-Migrationen (Flyway/Liquibase) gehören dem Backend-Agent.
  - **Bewusst deferred (kommen mit Last/Skalierung, nicht v1):** **Kafka** (Event-Streaming), **Redis** (Cache/Sessions), **ClickHouse** (Analytics/Zeitreihen), **K8s/GCP** (Orchestrierung/Cloud).
  - **Laufzeit (Update 2026-06-19, PO): Docker-Compose** für den 08-Stack (Keycloak + Postgres + User-Service + Gateway-Build), license-free via **colima/podman** auf dem Mac Mini — reproduzierbar/Standard statt launchd-nativer KC/PG-Installation (= Schmerz). **Der Key-Proxy ([[0021]]/[[0022]]) bleibt launchd-nativ + separat**; beide hinter demselben Caddy. (Ursprünglich war v1 als launchd-Prozesse skizziert; ersetzt.)
- **🔑 Auth-Grenze (verbindlich, [[0005]]):** Die **Platform-Auth (Keycloak)** ist **strikt getrennt** von der **non-custodial Wallet**.
  - **Seed/Private-Keys bleiben on-device** ([[0005]]/[[0009]]); das Backend **sieht sie nie**, speichert sie nie, signiert nie. Keycloak verwaltet **Platform-Accounts** (für Social/Feed/Copy-Follow/Strategie-Config), **nicht** Wallet-Schlüssel.
  - **Zwei getrennte Identitäts-Sphären:** (1) **Wallet-Identität** = die EVM-Adresse, kryptografisch on-device. (2) **Platform-Identität** = der Keycloak-Account. Wie (1)↔(2) verknüpft werden (z. B. **SIWE / Sign-In-With-Ethereum**: die Wallet **signiert on-device** eine Challenge → Keycloak föderiert den Adressbesitz, **ohne** je einen Key zu sehen) ist die zentrale offene Frage (s. u.) — die Invariante bleibt in jedem Fall: **Auth ≠ Custody**.
  - **Automatisierung (05–07) ohne Backend-Custody:** DCA/Copy-Trading/Vaults dürfen **keine** Backend-gehaltenen Keys nutzen. Delegation läuft über **on-device-Signatur auf Backend-Signal** oder **Smart-Contract-Delegation (Session-Keys / Account-Abstraction)** — Mechanismus = eigener Folge-ADR. Das Backend orchestriert **Signale/State**, nie Schlüssel.
- **Konsequenzen:**
  - **Single-Host-Verfügbarkeit** (wie [[0022]] R2): ein Mac Mini = ein Punkt → **FR-4-Degrade** (Platform-Features degradieren sauber/read-only statt Crash, wenn das Backend weg ist; die **Wallet-Kern-Funktionen — Receive/Send/Balances — bleiben unabhängig funktionsfähig**, da on-device + Key-Proxy). Monitoring/Auto-Restart (launchd, [[0022]] C). **Cloud-Exit:** Gateway/Keycloak/Postgres sind Standard-Komponenten → Lift-and-Shift in die Cloud, wenn Last/HA es fordern.
  - **PII/Datenschutz:** User-Service + Postgres halten **personenbezogene Daten** (Profile, Social-Graph). DSGVO-Posture (Verschlüsselung-at-rest, Backups, Lösch-/Auskunfts-Pfade, Standort des Hosts) = vor GA zu klären.
  - **Ownership-Grenze:** **Backend-Agent = Plattform/Infra** (Gateway, Keycloak, User-Service, Postgres, Deploy/Härtung, API-Contracts). **Feature-Dev-Bots = Feature-Services 04–07 + Smart-Contracts**, die **gegen die API-Contracts** des Gateways bauen. Contracts (OpenAPI/Proto) sind die Naht.
- **Alternativen (verworfen / aufgeschoben):** **Full-Stack sofort** (Kafka/Redis/ClickHouse/K8s/GCP von Tag 1) — verworfen: massiver Ops-Overbau für GA-Volumen, verzögert die Super-App ohne Nutzen; die vier v1-Bausteine decken Auth+Profil+Routing, der Rest kommt last-getrieben. **Backend-Custody / Server-side-Keys für Automatisierung** — verworfen (bricht [[0005]]). **Eigener zweiter Host für das Backend** — aufgeschoben (der Mac Mini trägt v1; Trennung kommt mit der Cloud-Migration). **Auth in den Key-Proxy integrieren** — verworfen (Key-Proxy bleibt auth-frei/read-only; Vermengung erhöht die Angriffsfläche auf dem Schlüssel-Pfad).

## Offene Fragen / Lücken (an den PO/User — vor Backend-Agent-Start zu klären)
1. **🔑 Identitäts-Verknüpfung Wallet↔Platform (die zentrale Design-Frage):** **SIWE** (Wallet signiert on-device, Keycloak föderiert die Adresse — wallet-zentrisch, kein zweites Passwort) **vs.** **getrennter Email/Social-Login** (Platform-Account unabhängig von der Adresse) **vs.** beides? Bestimmt das ganze Auth-Modell + UX. *(Assistenten-Tendenz: SIWE als primär — hält die Non-custodial-Story konsistent, eine Identität; Email/Social optional als Recovery/Komfort.)*
2. **Automatisierungs-Mechanismus 05–07 (Folge-ADR):** Session-Keys / Account-Abstraction (ERC-4337) / on-device-Signatur-auf-Signal? Das ist non-custodial-kritisch und rahmt DCA/Copy/Vaults-Architektur — eigener ADR vor PRD-05.
3. **DSGVO/PII:** Host-Standort (Oakhost — EU?), at-rest-Verschlüsselung Postgres, Lösch-/Auskunfts-Pfade, Backup-Posture für PII (anders als der Key-Proxy, der keine PII hält).
4. **Gateway↔Key-Proxy-Koexistenz:** beide hinter demselben Caddy als getrennte Routes (Empfehlung) — bestätigen; teilen sie Rate-Limit/Observability?
5. **Welche Feature-Services sind v1 vs. deferred?** User-Service ist v1; sind Market-Data (04)/DCA (05)/Copy (06)/Vaults (07) **alle** Erst-GA oder gestaffelt? Das bestimmt, was der Backend-Agent zuerst contractet.
6. **Secrets:** Keycloak-Admin/Realm, Client-Secrets, DB-Credentials → env/sysprop auf dem Host, nie im Repo (wie [[0021]]/[[0022]] E); `HARDENING.md`-Erweiterung.

## Update (2026-06-19) — Offene Fragen entschieden (PO, via DECISION-PACKAGE-v1)
Die sechs Fragen sind beantwortet; der Backend-Agent hat das v1-Skelett darauf gebaut:
1. **Identität = SIWE** (primär; Email = optionaler Recovery-Kanal, kein Platform-Passwort). Integration in Keycloak → **eigener [[0026]]** (SIWE-Keycloak).
2. **Automatisierung = ERC-4337 AA + scoped Session-Keys** als Ziel; v1-DCA interim Backend-Signal→on-device-Sign → **[[0024]]** (eigener ADR vor PRD-05). Infra-Scaffolding davon unberührt.
3. **DSGVO:** Host = Oakhost (EU); Postgres at-rest-verschlüsselt; Lösch-/Auskunfts-Pfade dokumentiert (`HARDENING.md`).
4. **Gateway↔Key-Proxy:** derselbe Caddy, **getrennte Routes/Prozesse**, getrennte Rate-Limit-Buckets; Key-Proxy bleibt auth-frei/read-only. (Bestätigt.)
5. **Feature-Service-Scope:** GA = alle 04–07; Build-/Contract-Reihenfolge gestaffelt (Auth + User-Service + Market-Data 04 zuerst → 05–07 nach dem Automatisierungs-ADR).
6. **Secrets:** Host-env (launchd `EnvironmentVariables` / chmod-600), nie im Repo. (Bestätigt.)
