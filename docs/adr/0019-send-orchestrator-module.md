# ADR-0019 — `:send`-Modul: ein Send-Orchestrator (In-App + WalletConnect)

- **Status:** **Accepted** (2026-06-18, KAN-91) — Send-Flow; realisiert im Modul `:send`, PO-reviewt. *(Hinweis: 0019 war in PRD-04 vorläufig für die Charting-ADR vorgemerkt — die rückt damit auf **0020**; PRD-04-Referenzen entsprechend nachziehen.)*
- **Kontext:** Eine Transaktion zu senden verbindet **L2** (`:wallet`-Signatur, [[0014]]), **L3** (`:rpc` — nonce/fees/gas/broadcast/receipt, [[0010]]), **`:storage`** (Unlock→`SecureSeedSource`, [[0009]]) und — sobald gemergt — **`:walletconnect`** ([[0015]]). Zwei Eingänge erzeugen denselben Bedarf: **In-App-Send** (User wählt to/asset/amount) und **WalletConnect `eth_sendTransaction`**. Diese Module dürfen sich **nicht** gegenseitig referenzieren; die Orchestrierung gehört in eine eigene Schicht ([[0002]] Clean/MVVM). Send ist **sicherheitskritisch** (non-custodial, [[0005]]): „sign what you saw", kein Blind-Signing, minimales Seed-Fenster.
- **Entscheidung:** Ein **dediziertes Feature-Modul `:send`** mit **einem** `SendOrchestrator` für **beide** Eingänge (beide produzieren ein normalisiertes `SendInput`). Zweiphasig, damit Disclosure/Approval sauber zwischen Vorbereitung und Signatur liegen:
  - **`prepare(input, accounts)` → `PreparedSend(tx, accountIndex, disclosure)`** (vor Approval): Account auflösen → completen (nur fehlende Felder) → Balance validieren → Disclosure der **fertigen** Tx.
  - **`signAndBroadcast(prepared, seedSource)`** (nach Approval): signiert **exakt** `prepared.transaction`, **zeroized den `SeedSource` sofort** (`finally`), broadcastet.
  - **Fünf Guardrails (verbindlich):**
    1. **TOCTOU / signed == disclosed:** completen + disclosen passieren in `prepare`; nach der Disclosure wird **kein** Fee/Gas/Nonce mehr gefüllt — `signAndBroadcast` signiert genau die disclosed Tx.
    2. **fill-not-override:** ein vom Aufrufer/dApp gesetztes Feld wird **nie** überschrieben; nur Fehlendes wird ergänzt.
    3. **Account-Binding:** `from` muss ein bekannter Wallet-Account sein; signiert wird mit dem **aus der Adresse aufgelösten** Derivations-Index (Signer-Adresse == `from` per Konstruktion) — sonst `AccountMismatch`.
    4. **Chain-Binding:** Tx wird auf `input.chain.chainId` gebaut **und** auf derselben Chain signiert/broadcastet — kein Chain-Swap.
    5. **fail-closed:** Decode-/Validierungs-Fehler werfen `SendError`; unbekannte Calldata → `Unknown(rawHex)` (UI zeigt Warnung, nie als „verstanden"). Node-Reject (Revert) → `TransactionRejected` **ohne Retry**; Transport → `NetworkError` (retrybar).
  - **Key-Pfad-Invariante ([[0005]]):** der Seed lebt **nur** in `signAndBroadcast` (prepare nutzt **public** `EvmAccount`s); Signatur in `:wallet`; der `SeedSource` wird unmittelbar nach dem Signieren zeroized (minimales In-Memory-Fenster). Disclosure decodiert ERC-20 `transfer`/`transferFrom`/`approve` menschenlesbar (kein Blind-Signing).
- **Konsequenzen:** `:send` ist Consumer von `:rpc`+`:wallet`(+später `:walletconnect`); diese bleiben entkoppelt. Der **WalletConnect-Adapter** (decode→`SendInput`, `respondSessionRequest`) lebt außerhalb von `:send` und **muss `SendInput.from`/`chain` aus der approved Session** speisen (nicht aus dApp-Params) — sonst greifen #3/#4 nicht; der Orchestrator erzwingt sie gegen `SendInput`. Balance-Check nutzt 256-bit-`Quantity`-Arithmetik (fail-closed bei Overflow). Receipt-Tracking via `EvmRpcClient.awaitReceipt` (aufrufer-getrieben).
- **Alternativen (verworfen):** Orchestrierung im App-ViewModel (koppelt App an alle vier Module, schwer testbar); **zwei** Orchestratoren (In-App vs. WC) — dupliziert die Guardrail-Durchsetzung, Drift-Risiko; Completion im `:walletconnect`-Transport (würde `:walletconnect`→`:rpc` koppeln, gegen [[0015]]/Schnitt).
