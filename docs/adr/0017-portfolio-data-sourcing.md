# ADR-0017 — Portfolio-Datenbeschaffung & Bewertung (`:portfolio`, on-device)

- **Status:** **Accepted** (2026-06-18) — Portfolio-Slice (PRD-03). Produkt-Calls (PO/User, 2026-06-18): **Q1 = weich** (Backend/ClickHouse entkoppelt, nur kanonisch/cross-device später); **Q2 = Rich on-device** (P&L + Sharpe/Max-Drawdown + zeitgewichteter Verlaufs-Chart als **Best-Effort-Approximation** mit dokumentiertem Accuracy-Caveat). PO-Abnahme erfolgt; im INDEX geführt.
- **Kontext:** PRD-03 aggregiert Holdings über alle Accounts × **Ethereum + Base** (gespiegelt zu [[0016]] / PRD-02) zu Gesamtwert, Allocation, Tx-Historie und Kennzahlen. Der frühere PRD-03-Stub setzte dies **hart** auf den PRD-08-Backend (Portfolio-Service + ClickHouse-**Analytics-Service**). Context7-Recherche (2026-06-18) zeigt: Alchemy bietet **on-device** nutzbare REST-APIs — **Data/Portfolio API** (`assets/tokens/balances/by-address`, Multi-Chain in **einem** Call; `getAssetTransfers`; NFT) und **Prices API** (Preise nach Symbol/Adresse **+ historisch** über Zeitbereich/`interval`). Portfolio ist **read-only** → braucht **kein** secp256k1 und ist damit **voll web-fähig** ([[0016]] zeigt: `:evm`+`:rpc` tragen Web read-only).
- **Entscheidung:**
  - **On-device-Datenbeschaffung im MVP** über die in [[0010]]/[[0016]] (`:rpc`, KAN-54) etablierte **Ktor-/Provider-Abstraktion + Failover** — erweitert um **REST-Clients** für Alchemy **Data API** und **Prices API** (zusätzlich zum bestehenden JSON-RPC). **Kein eigener Indexer** (The Graph/Custom) und **kein ClickHouse** im MVP.
  - **Neues Feature-Modul `:portfolio`** (Domain/Repository/ViewModels, [[0002]]/[[0003]]) auf **`:evm` + `:rpc`** ([[0016]]) aufsetzend; **web-fähig (inkl. js/wasm)**, da read-only. Data-/Prices-REST-Clients liegen im web-fähigen **`:rpc`** (bzw. einem `:rpc`-internen `data`-Paket), nicht in `:wallet` (non-web).
  - **`PriceSource`-Abstraktion** als einzige Bewertungsquelle: MVP = Alchemy Prices; **migrierbar** auf den PRD-04-Market-Data-Service (CoinGecko/Binance, Redis) ohne API-Bruch.
  - **Backend-Analytics = weich-gegatete spätere Schicht (Q1=weich):** Portfolio-/Analytics-Service + ClickHouse erst dort, wo **kanonische, geräteübergreifend persistente** Metriken nötig sind; liefert später die **kanonischen** Werte als Ablösung der on-device-Approximation. Kein MVP-Blocker.
  - **Rich-Metriken on-device (Q2=rich), deterministisch + test-vektor-geprüft (PRD-03 FR-6):** **robust on-device** = Gesamtwert, 24h-Veränderung, Asset-Allocation. **Rich** = echtes P&L, zeitgewichteter Verlaufs-Chart, Sharpe/Max-Drawdown — on-device via **Holdings-Rekonstruktion** aus `getAssetTransfers` + historische Preise (FIFO), als **Best-Effort-Approximation mit sichtbarem Accuracy-Caveat** (Cost-Basis-Ambiguität, fehlende/lückenhafte Transfer-Daten, ungeprüfte Spam-Token). Slice **P4** in PRD-03 §8.
- **Konsequenzen:** PRD-03 **vom PRD-08-Slice entkoppelt** — Start sobald **L1** ([[0016]] `:wallet`, KAN-52) + **L3** (`:rpc`, KAN-54) stehen. Portfolio wird **erstes voll web-fähiges Feature**. Bewertungsquelle gekapselt → späterer Wechsel auf PRD-04 lokal. Preis: Provider sieht abgefragte Adressen (Privacy-Note, PRD-03 NFR-3); Advanced-Metriken später bzw. as-approximation gekennzeichnet. **Feindetails zu [[0010]]** (REST neben JSON-RPC, Retry/Timeout/Rate-Limit für Data/Prices) werden in 0010 als Update vermerkt.
- **Alternativen (verworfen / aufgeschoben):** **Harter** Backend-Pfad (eigener Indexer + ClickHouse vor jeder Portfolio-Anzeige) — verzögert PRD-03 unnötig hinter PRD-08, widerspricht dem on-device-Befund. **Naiver Verlaufs-Chart** „aktuelle Bestände × historischer Preis" ohne Holdings-Rekonstruktion — analytisch falsch (ignoriert vergangene Trades), daher ausgeschlossen. **NFT-Bewertung** (Floor) im MVP — unzuverlässig, aufgeschoben (PRD-03 §2).
