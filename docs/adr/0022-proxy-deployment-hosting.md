# ADR-0022 — Proxy-Deployment: gehosteter Key-Proxy (Mac Mini @ Oakhost, TLS)

- **Status:** **Accepted** (2026-06-19, KAN-125) — Prod-Deployment des Key-Proxys aus [[0021]]; Deployment-Ziel vom User entschieden (Mac Mini @ Oakhost, TLS). Ergänzt [[0021]] (das *was/warum* des Proxys; dieses ADR das *wo/wie* in Prod).
- **Kontext:** [[0021]] hat den Alchemy-Key aus dem Client entfernt, indem ein `:server`-Proxy ihn server-seitig injiziert — bewusst **lokal** (`http://localhost:8080`, dev). Für **GA mit ausgelieferten Clients** (Android **und** iOS, G4) ist „lokal" untauglich: ein installierter Client kann nicht gegen `localhost` sprechen; er braucht eine **stabile, öffentlich erreichbare, TLS-gesicherte URL**. Damit ist das Deployment-Modell ein **P0-GA-Blocker** (KAN-125). Randbedingungen: non-custodial ([[0005]]) — der Proxy bleibt **read/broadcast-only** Transport, **kein** Seed/Key passiert ihn (Key-Pfad-Invariante aus [[0021]] gilt unverändert).
- **Entscheidung:** Der Proxy läuft als **dauerhaft erreichbarer Dienst auf einem gemieteten Mac Mini (Oakhost)** mit **öffentlicher URL + TLS**; alle Clients sprechen ausschließlich diese URL (`AlchemyProxyConfig.proxyBaseUrl` = die Prod-URL statt `localhost`). Verbindlich (KAN-125):
  - **(A) Öffentliche URL + TLS-Terminierung.** Stabiler DNS-Name; HTTPS erzwungen (HTTP→HTTPS-Redirect/HSTS). Zertifikat via Let's Encrypt mit **Auto-Renewal**. Empfohlen: ein **Reverse-Proxy (Caddy/nginx)** vor dem Ktor-Netty-Prozess übernimmt TLS + die Hardening-Header, statt TLS im Ktor-Prozess.
  - **(B) Reverse-Proxy ⇒ Rate-Limit auf `X-Forwarded-For`.** Hinter (A) ist `request.local.remoteHost` die Proxy-IP → der [[0021]]-Rate-Limiter **muss** den echten Client aus `X-Forwarded-For` (nur vertrauenswürdige Hops) lesen, sonst kollabiert das Limit global. + Window-Map-Eviction (sonst unbounded Memory).
  - **(C) Prozess-Supervision + Auto-Restart** (launchd/`pm2`/systemd-Äquivalent) + Boot-Persistenz; **fail-closed** Health (`/healthz` für Uptime-Monitoring; Alerting bei Down).
  - **(D) Netzwerk-Minimierung:** nur 443 (und ggf. 80 für ACME) offen; SSH gehärtet; der Ktor-Port (8080) **nicht** öffentlich, nur lokal hinter dem Reverse-Proxy.
  - **(E) Key-Hygiene unverändert ([[0021]]):** Alchemy-Key aus Env/sysprop auf der Maschine (nie im Repo/Image); Upstream-URL (enthält den Key) **nie loggen**; Request-Bodies/Adressen sind PII-arm, aber Access-Logs auf das Nötige begrenzen.
  - **(F) `HARDENING.md`** committen: Runbook für Deploy, Cert-Renewal, Key-Rotation, Restart, Monitoring, Incident.
- **Konsequenzen:** Clients (Android+iOS) funktionieren in Prod ohne Client-Key; die [[0021]]-Hardening-Items (X-Forwarded-For, Max-Body, Tail-Allowlist KAN-115 ✅, never-log-key) werden mit (A)–(F) **scharf geschaltet**. **Neues Haupt-Risiko = Verfügbarkeit/Single-Host:** ein Mac Mini ist **ein** Punkt — Ausfall/Wartung/Netz ⇒ **alle** Clients ohne Daten. Mitigation: **FR-4-Degrade** (Clients zeigen `Approximate`/stale statt Crash, [[0021]] (E) `503`-Pfad) + Uptime-Monitoring/Alerting; **Skalierungs-/HA-Limit bewusst akzeptiert** für GA-Volumen, mit Cloud-Migration als Exit (s. Alternativen). Betriebslast (Patching/Cert/Key-Rotation/Monitoring) liegt beim Team — daher (F). Latenz: ein einzelner Standort ⇒ Geo-Latenz für entfernte Nutzer (für GA vertretbar).
- **Alternativen (verworfen / aufgeschoben):** **Embedded-Key im Client** (verworfen — der ursprüngliche Auslöser von [[0021]]: extrahierbar). **Separater Cloud-Anbieter / Managed-Hosting** (aufgeschoben — mehr HA/Geo/Autoscale, aber Kosten + Setup; der Mac Mini deckt GA-Volumen, **Cloud bleibt der Skalierungs-Exit**, wenn Last/HA es fordern — `AlchemyProxyConfig.proxyBaseUrl` macht den Wechsel zu einer reinen URL-Änderung). **TLS im Ktor-Prozess statt Reverse-Proxy** (möglich, aber Reverse-Proxy ist robuster für Cert-Renewal/Header/Port-Isolation). **Serverless/Edge-Functions** (aufgeschoben — gutes HA/Geo, aber Cold-Start + Anbieter-Bindung; später erwägen).
