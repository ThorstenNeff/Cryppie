# ADR-0026 — SIWE-Keycloak-Integration: Custom Authenticator-SPI + `siwe-java`

- **Status:** **Accepted** (2026-06-19, PRD-08) — Empfehlung des Backend-Agenten, vom PO ratifiziert. Ergänzt [[0023]] (Backend-Blueprint, F1=SIWE) und [[0005]] (non-custodial). Voraussetzung für den Auth-Bau.
- **Kontext:** [[0023]] legt **SIWE (Sign-In-With-Ethereum, EIP-4361)** als Platform-Identität fest (F1): die Wallet-Adresse **ist** die Identität, kein zweites Passwort. SIWE-Flow: die Wallet signiert **on-device** eine strukturierte Challenge; das Backend verifiziert den **Adressbesitz** und stellt ein Session-JWT aus — **ohne je einen Key zu sehen** (**Auth ≠ Custody**, [[0005]]). Offen war: **wie** SIWE in Keycloak integrieren, und wie die **sicherheitskritische SIWE-Korrektheit** (Nonce, Domain-Binding, Replay-Schutz, Chain-ID-Binding, Signatur-Recovery) garantieren. Keycloak ([[0023]] B) ist der OIDC-Provider, den die KMP-Clients ohnehin sprechen.
- **Entscheidung:** Ein **Custom Keycloak Authenticator-SPI** (`AuthenticatorFactory` + `Authenticator`, als Provider-JAR ins KC-Image), der die **EIP-4361-Parsing + Signatur-Verifikation an die gepflegte Java-Lib `moonstoneid/siwe-java`** delegiert (Spruce `siwe-rs`/`siwe-go` als Referenz-Implementierungen). Der SPI ist der offiziell dokumentierte, gegen unser **Keycloak 26** pinbare Erweiterungsweg; die Krypto wird **nicht** hand-gerollt und **kein** All-in-One-Community-Plugin verwendet (keins prominent/gepflegt gegen KC 26 — den Identitäts-Kern nicht auf ungepflegten Drittcode bauen).
  - **Realm/Client:** dedizierter `cyppie`-Realm; ein **public OIDC-Client + PKCE** für die KMP-App; ein **Custom-Authentication-Flow** mit dem SIWE-Authenticator als `REQUIRED`-Step.
  - **Flow:**
    1. **Challenge:** Client fordert eine Challenge an → der Authenticator gibt eine **single-use Nonce** mit kurzer Expiry aus, gebunden an die Auth-Session.
    2. **Sign:** Client baut die EIP-4361-Message (`domain`, `address`, `statement`, `uri`, `version`, **`chainId`**, **`nonce`**, `issuedAt`, `expirationTime`) → Wallet signiert **on-device**.
    3. **Verify** (im SPI, via `siwe-java`): Signatur-Recovery → `recovered == claimed address`; **`domain` == unsere** (Domain-Binding/Anti-Phishing); **Nonce** existiert, unbenutzt, nicht abgelaufen → als **verbraucht markieren** (Replay-Schutz); **`chainId`** erlaubt; `issuedAt`/`expirationTime` im Fenster.
    4. **Föderieren:** finde/erzeuge den Keycloak-User mit Schlüssel = **lowercase EVM-Adresse** → `context.success()` → Keycloak stellt das **RS256-JWT** (Realm-Keys) aus. Eine optionale Email wird als separater Recovery-/Notification-Identity-Link geführt — **nie** als Wallet-Zugang.
  - **Nonce-Store v1:** Keycloaks eingebauter `SingleUseObjectProvider` / Auth-Session-Note — **kein** zusätzliches Redis nötig (Redis ist deferred, [[0023]]).
  - **JWT-Durchsetzung:** Caddy validiert das RS256-JWT gegen die Realm-**JWKS** auf den `/v1`-Routes (F4), **und** der User-Service validiert erneut (defense-in-depth). Keine Tokens ohne gültige Realm-Signatur erreichen einen Upstream.
- **Konsequenzen:**
  - **SIWE-Korrektheit** (Nonce/Domain/Replay/Chain-ID) liegt in **unserem auditierbaren SPI**, gegen KC 26 gepinnt; die Krypto kommt aus einer **fokussierten, EIP-4361-spezifischen Lib** (kleinere Fehlerfläche als Eigenbau).
  - **Build/Deploy:** Das Provider-JAR muss ins Keycloak-Image (`/opt/keycloak/providers/`) + `kc build` → das `keycloak`-Compose-Service braucht ein **eigenes Image** (Multi-stage: Provider bauen → ins KC-Image backen → `start --optimized`), statt des reinen `quay.io`-Images. (Das aktuelle Skelett nutzt noch das reine Image; wird mit dem Auth-Bau ersetzt.)
  - **Maintenance:** Wir tracken `siwe-java` + die **KC-SPI-API über Major-Upgrades** (das SPI kann zwischen KC-Majors brechen) — kalkuliert, da Auth-Kern; an KC 26 gepinnt.
  - **Recovery-Trade-off:** reines SIWE = „Seed/Gerät weg → Platform-Identität weg", **gemildert**, weil Plattformdaten an die **Adresse** hängen (beim Seed-Re-Import auf neuem Gerät wieder erreichbar); optionaler Email-Link als Komfort-Recovery.
  - **Anti-Phishing:** das erzwungene Domain-Binding macht Signaturen für andere dApps **nicht wiederverwendbar**.
- **Alternativen (verworfen / aufgeschoben):**
  - **All-in-One Community-Keycloak-SIWE-Plugin** — *verworfen:* kein prominentes, gegen KC 26 gepflegtes Plugin auffindbar; ungepflegter Drittcode für den Identitäts-Kern = falsches Risiko (das Fehlen IST das Signal).
  - **Signatur-Verifikation selbst hand-rollen** (secp256k1/ecrecover von Hand) — *verworfen:* unnötige Krypto-Fehlerfläche; `siwe-java` deckt EIP-4361 fokussiert ab.
  - **SIWE außerhalb Keycloak** (eigener Auth-Service, der JWTs ausstellt) — *verworfen:* dupliziert KCs Token-/Realm-/Client-Management; das SPI integriert SIWE sauber in den OIDC-Flow, den die KMP-Clients ohnehin nutzen.
  - **DIY-Nonce-Store in Redis** — *aufgeschoben:* KC `SingleUseObjectProvider`/Auth-Session reicht für v1 (Redis deferred, [[0023]]).
